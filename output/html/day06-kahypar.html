KaHyPar Project Study · Day 06

Uncoarsening & Refinement：
恢复自由度，再只保留好移动

最粗层的解只是起点。KaHyPar 逆序恢复每一次 contraction，把代表点和被收缩点交给局部搜索；FM 用增益队列探索单点移动，flow 则在相邻块之间寻找成组改进。

驱动 doUncoarsen局部 FM gain cache成组 HyperFlowCutter
01 · Goals

把“逐层改进”读成真实状态变化

恢复说明为何 parallel edge、single-node edge 要在 uncontract 前恢复。
投影理解新恢复节点先继承代表点的 part ID。
FM解释 activate、gain queue、move、更新邻居与停止策略。
Rollback知道为何执行过负 gain 移动后，最终质量仍不变差。
02 · Uncoarsening

金字塔不是一次展开，而是一层一层放大

原始超图最多节点，最终输出
↑ uncontract + refine
中间层恢复一个点对
↑ uncontract + refine
粗层较少自由度
↑ initial partition
最粗层先得到 part IDs

VertexPairCoarsenerBase::doUncoarsen 从粗层 cut、km1、imbalance 初始化 Metrics，随后对 _history.back() 反复执行恢复和细化，直到 history 为空。

while (!history.empty()) {
  refinement_nodes = { memento.u, memento.v };
  uncontract(changes);
  performLocalSearch(refiner, refinement_nodes, metrics, changes);
}
03 · Restore Order

一次恢复的顺序不能交换

parallel edges恢复被合并边
single-node edges恢复被删除边
max weight回退层级记录
uncontract恢复节点与 pins
pop history消费 memento

pruner 的恢复数据依附于该次 contraction 的 memento，所以必须在它仍是 history.back() 时逆序还原。之后 Hypergraph::uncontract 激活被收缩节点，并把代表点的分区投影给它。

2-way FM 特例 对 twoway_fm 及其 flow 组合，uncontract 还计算 UncontractionGainChanges，让 gain cache 做增量修正；其他 refiner 走普通恢复重算路径。
04 · FM Loop

FM 是“最高收益优先”的受约束搜索

activate
把刚恢复的两个节点加入候选；若涉及 fixed vertex，再激活相邻自由节点。
initialize gain cache
为可达目标块计算移动后的 objective 变化，放入 k-way priority queue。
deleteMax
取出当前 gain 最大的 (node,to_part)。
feasibility
目标块加上节点权重不能超过 Lmax，来源块不能被移空。
move + update
changeNodePart 后只增量更新受 incident edges 影响的邻居。
stop
队列空或 stop policy 判断继续搜索收益不足。
gain(v : A → B) = objective(before) - objective(after)
gain > 0 表示移动使目标函数下降

FM 允许暂时选择 gain 为 0 或负数的 move，因为它可能打开后续更好的组合路径。安全性由“记录最好前缀并回滚尾部”保证。

05 · Best Prefix

为什么做了坏移动，最后仍不会更差

假设初始 km1 为 12，一轮移动的 gain 依次为 +2, -1, +3, -2：

前缀当前 km1是否刷新 best
起点12best = 12，index = -1
move 010best = 10
move 0..111否，但保留探索
move 0..28best = 8
move 0..310否

循环结束后，rollback(last_index, min_cut_index) 逆向执行尾部 move。例中只撤销最后一个 -2 move，留下 km1=8 的最佳前缀。

索引语义 源码在刷新 best 时把 min_cut_index 设为已执行 move 数；回滚从最后一个下标走到该边界。读代码时要区分“元素下标”和“已执行数量”。
06 · Gain Cache

km1 gain 为什么依赖 connectivity 变化

对超边 e，km1 贡献是 (lambda(e)-1) × weight(e)。节点从 A 移到 B 时，只有它的 incident edges 可能改变：

局部事件lambda 变化对 km1 的影响
v 是 A 中最后一个 pin，B 已有 pin-1gain +weight(e)
A 仍有其他 pin，B 原来无 pin+1gain -weight(e)
A 消失且 B 新出现0贡献不变
A、B 均已存在且 A 不消失0贡献不变

pinCountInPart 与 connectivitySet 让这些判断不必重新扫描整张图。每次 move 后，refiner 根据临界 pin count 更新邻居缓存。

07 · Flow

FM 找单点路径，flow 找成组切割

FM refinement候选是一个节点移到一个相邻块；快，适合频繁逐层调用。
Flow refinement围绕两个块的边界抽取子问题，用最小割同时决定一组节点去向。

k-way flow 先根据 cut hyperedges 构建 quotient graph：块是节点，共享 cut hyperedge 的块对构成边。scheduler 打乱块对并做 active-block rounds，只重新处理受改进影响的块。

flow_refiner.refine(...)
if (flow_improvement) {
  moves = flow_refiner.rollbackPartition();
  fm_refiner.performMovesAndUpdateCache(moves, ...);
}
fm_refiner.refine(...)

组合 refiner 的顺序是 flow 后 FM。flow 产生的一组 move 还要同步到 FM gain cache，随后 FM 再清理局部残余机会。

09 · Practice

练习与答案核对

  • 为什么 uncoarsening 只把 memento 中的两个节点作为首批 refinement nodes？
  • 一个权重为 3 的节点要从重量 7 的块移入 Lmax=9、当前重量 6 的块，是否可行？
  • 手算 gain 序列 +1,-2,+4,-1 从 objective=10 开始的最佳前缀。
  • 说明 flow 改进后为何必须更新 FM gain cache。
  • 解释 recursive + km1 时为什么 uncoarsening 结束后显式重算 km1。
1. refinement nodes

刚刚恢复的点对是本层新增自由度和局部结构变化的中心。先从它们激活候选，可把每层搜索限制在受影响区域；后续邻居会按需被激活。

2. 平衡判断

可行，目标块变为 9，刚好不超过 Lmax。还需确保来源块不会因移动变成空块。

3. 最佳前缀

objective 依次为 9、11、7、8，最好是前三个 move 后的 7；回滚最后一个 move。

4. cache 同步

flow 会同时改变多个节点 part ID，旧 gain 都基于变化前的 pin counts。组合 refiner 先拿到 move 列表，再让 FM 按同样顺序更新缓存，避免使用过期收益。

5. RB 的 km1

recursive bisection 的 2-way FM 优化 cut，并通过 cut-net splitting 间接服务 km1；循环中没有持续维护 k-way km1，所以结束时调用 metrics::km1 得到正确结果。
