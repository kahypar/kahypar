01 · Orientation

今天要跨过“参数只是参数”的错觉

在 KaHyPar 中，配置不只是控制几个 if 分支。它先进入结构化 Context，经过输入规模派生出新参数，再作为枚举键和策略键，决定真正构造哪个算法对象。

01读懂 `.hgr`解释 header、权重类型、1-based 到 0-based 转换和 sentinel。
02画出 Context区分 partition、preprocessing、coarsening、initial partitioning 和 local search。
03算出派生参数由 n、总重量、k、epsilon、s、t 得到停止阈值和平衡上限。
04追到具体类型从 ini 字符串走到 enum、Factory callback，再到带策略模板参数的实例。

02 · Entry

main() 的三段启动链路

第一天见过这个入口；现在我们给每一行补上“数据形态”。

processCommandLineInput(context, argc, argv)字符串与数值 → 结构化 Context
createHypergraphFromFile(filename, k, ...)文本行 → vectors → Hypergraph
PartitionerFacade().partition(hypergraph, context)按输入规模补全 Context，检查组合合法性
Factory::createObject(enum, ...)配置枚举 → ICoarsener / IRefiner / IInitialPartitioner
kahypar/application/kahypar.cc
Context context;
processCommandLineInput(context, argc, argv);

Hypergraph hypergraph(
  io::createHypergraphFromFile(context.partition.graph_filename,
                               context.partition.k,
                               VALIDATE_INPUT,
                               PROMOTE_WARNINGS_TO_ERRORS));

PartitionerFacade().partition(hypergraph, context);
所有权也值得注意Hypergraph 与 Context 都在 main 的栈上；工厂创建的算法对象通常用 std::unique_ptr<I...> 管理，并持有对这两者的引用。
03 · Input Format

hMetis `.hgr`：第一行决定后续语法

header 形如 m n [fmt]：先写超边数 m，再写超节点数 n。第三列可省略，默认无权；注意顺序不是 n、m。

0无边权 / 无点权
1有超边权
10有节点权
11边权与点权都有
fmt接下来的 m 行超边之后
0 / 省略每行只有 pin IDs文件结束
1第一个数是 edge weight，其后是 pins文件结束
10每行只有 pins再读 n 行，每行一个 node weight
11edge weight + pins再读 n 行 node weights
四种输入的最小形态
% 无权：4 条边，7 个点
4 7
1 2
...

% 边权：超边行首的 2 是权重
4 7 1
2 1 2
...

% 点权：4 条边后继续读取 7 行权重
4 7 10
1 2
...
5
1
...
  • 以 % 开头的整行会被 getNextLine 跳过。
  • 文件中的节点 ID 从 1 开始；解析器遇到 0 会报错。
  • 读取每个 pin 后立刻执行 --pin，内部统一使用 0-based ID。
  • 空超边是错误；末尾额外的非空内容会触发 warning。
04 · Worked Parse

手工解析仓库中的 7 节点输入

文件视角 · 1-based

header4 7
e01 2
e11 7 5 6
e25 6 4
e32 3 4
→

内存视角 · 0-based

e0{0, 1}
e1{0, 6, 4, 5}
e2{4, 5, 3}
e3{1, 2, 3}
pins总数 12

每读一条超边，解析器先把当前 edge_vector.size() 写入 index_vector；读完该边后，再追加新的 size。最后自然得到 m+1 个边界。

解析结果 · 与 hypergraph_io_test 期望一致
index_vector = [ 0, 2, 6, 9, 12 ]
edge_vector  = [ 0,1,  0,6,4,5,  4,5,3,  1,2,3 ]
                 └e0┘  └──e1──┘  └─e2─┘  └─e3─┘

pins(e) = edge_vector[index_vector[e] ... index_vector[e+1])
sentinel 不是多余元素index_vector[4]=12 不代表第 5 条边，而是 e3 的右边界。没有它，最后一条边就无法使用与其他边相同的区间公式。

解析与校验是两层

readHypergraphFile 负责语法和基础读取；createHypergraphFromFile 可选择调用 validateInput。校验发现重复 pins 时会把相应位置加入 ignored_pins，构造 Hypergraph 时跳过；严重错误则退出。

05 · Configuration

Context 是一棵分层配置树

它同时存放用户输入、preset 选项、运行中派生值和少量状态。字段按算法阶段组织，而不是按“来自命令行还是 ini”组织。

TOP LEVEL

partition

mode、objective、k、epsilon、seed、文件名、块重量、V-cycles。

PREPARE

preprocessing

社区检测、min-hash sparsifier、去重及它们的阈值。

MULTILEVEL

coarsening

粗化算法、评分 policies、停止规模和最大节点重量。

COARSEST

initial_partitioning

自己的 mode、technique、algorithm，以及嵌套的粗化/细化配置。

UNCOARSEN

local_search

refiner、FM 停止规则、flow 调度和 HyperFlowCutter 参数。

OPTIONAL

evolutionary

种群、mutation/combine 策略、父代引用和 edge frequency。

配置装载顺序

C1注册 optionspo::value(&context.field) 直接绑定普通字段；字符串算法名用 notifier 转 enum。
C2解析命令行先 store(parse_command_line)，再立即 notify。
C3读取 preset打开 -p 指定的 ini，向同一个 variables_map 补充配置，再 notify。
C4生成输出名按 graph、k、epsilon、seed 生成默认 partition filename。
这个版本的一个实际细节mode 和 objective 被声明为 required，而且第一次 notify 发生在读取 preset 之前。因此 CLI 运行时仍要显式提供 -m、-o；只写在 ini 中不够。-h/-k/-e 也同样是命令行必需项。
覆盖关系命令行先进入 variables_map，preset 补充其余项；实测 --seed 42 会覆盖 ini 中的 seed=-1，CLI 的 mode 也会覆盖 preset 的 mode。
06 · Derived Values

Context 读完文件后还会“长出”新值

用户配置无法预先知道超图总重量，所以 Partitioner::setupContext 在拿到 Hypergraph 后计算停止条件和平衡上限。以仓库 7 节点无权图、k=2、epsilon=0.03，以及 preset 中 t=160、s=3.25 为例：

派生值公式本例结果
粗化停止点contraction_limit = t × k160 × 2 = 320
节点重量比例fraction = s / contraction_limit3.25 / 320 = 0.01015625
可收缩最大节点重量ceil(fraction × totalWeight)ceil(0.07109) = 1
完美块重量Lopt = ceil(totalWeight / k)ceil(7/2) = 4
允许块重量Lmax = (1+epsilon) × Lopt整数权重容器中显示为 4
配置参数 + 输入规模 → 可执行的算法约束同一个 ini 用在不同规模的图上，会得到不同 contraction limit 相关状态和块重量上限。
为什么本例没有真的缩到 320 个点？初始只有 7 个节点，本来就不大于停止阈值 320，因此 coarsener 无需继续收缩。这也是实际运行输出里 coarsened graph 仍有 7 个节点的原因。
07 · Factory

字符串如何最终变成一个模板实例

KaHyPar 同时使用两级选择：普通 Factory 根据算法枚举选“大类”，StaticMultiDispatchFactory 再根据多个 policy 的运行时对象，匹配出已经编译的模板参数组合。

INI 字符串c-type=heavy_lazy人可读、便于实验配置
→
Context 枚举CoarseningAlgorithm::heavy_lazynotifier 调用 fromString 转换
→
Factory 产品unique_ptr<ICoarsener>实际对象是带具体 policies 的模板实例
F1编译期注册REGISTER_DISPATCHED_COARSENER 定义静态 Registrar。
F2程序启动Registrar 构造，把 enum → creator lambda 写入单例 Factory 的 unordered_map。
F3算法阶段createObject(context.coarsening.algorithm, hg, context, maxWeight) 查表调用 lambda。
F4策略匹配lambda 从 PolicyRegistry 取得评分、惩罚、社区、acceptance 等 policy 对象。
F5具体构造StaticMultiDispatch 用 dynamic_cast 匹配 policy 类型，执行 new LazyVertexPairCoarsener<Policies...>。
核心机制的压缩视图
// 1. 注册 enum → creator
REGISTER_DISPATCHED_COARSENER(CoarseningAlgorithm::heavy_lazy,
                              LazyCoarseningDispatcher, policies...);

// 2. 运行时按 enum 查表
auto coarsener = CoarsenerFactory::getInstance().createObject(
  context.coarsening.algorithm, hypergraph, context, max_weight);

// 3. dispatch 最终构造编译期模板组合
return new LazyVertexPairCoarsener<MatchedPolicies...>(
  hypergraph, context, max_weight);
Factory键抽象产品创建位置
CoarsenerFactoryCoarseningAlgorithmICoarsenerdirect_kway.h / multilevel.h
RefinerFactoryRefinementAlgorithmIRefiner与 coarsener 成对创建
InitialPartitioningFactoryInitialPartitionerAlgorithmIInitialPartitionerinitial_partition.h
BinPackerFactoryBinPackingAlgorithmIBinPacker预打包和递归二分
这套设计解决的矛盾研究代码希望通过 ini 灵活切换策略，但 C++ 模板又需要编译期类型。注册表负责运行时的大类选择，multi-dispatch 把 policy 运行时对象重新落到一个已编译的模板组合上。
08 · Experiment

真实 CLI：观察覆盖与动态配置

在仓库根目录运行
build/kahypar/application/KaHyPar \
  -h tests/io/test_instances/unweighted_hypergraph.hgr \
  -k 2 -e 0.03 \
  -p config/cut_rKaHyPar_sea20.ini \
  -m direct -o cut \
  --seed 42 --verbose true --write-partition false

这个 preset 原本是 recursive 且 seed=-1；输出 Context 却显示 direct、cut、seed=42，证明命令行值获胜。输出还显示输入规模 7/4/12、Lopt=4、contraction limit=320、最大节点重量=1，和上一节手算一致。

观察点输出来源

随机种子seed: 42CLI 覆盖 ini 的 -1
输入规模#HNs 7 / #HEs 4 / #pins 12HGR 解析结果
平衡目标L_opt=4 / L_max=4setupPartWeights

实验里的警告怎么理解我们故意用 recursive preset 再以 CLI 改成 direct，preset 中的 two-way refiner 与 direct 模式组合不自然，因此程序发出兼容性警告。正常使用应选择与 mode/objective 成套的 preset；这个混搭只用于观察配置覆盖。

动手题

  • 把 weighted_hyperedges_hypergraph.hgr 的第一条超边手工解析成 edge weight 和 0-based pins。
  • 只给 preset、不传 -m/-o 运行一次，解释 required option 为什么在读取 ini 前触发。
  • 把命令中的 --seed 42 改为 7，确认默认输出文件名同步变化。
  • 从 r-type=kway_fm_km1 出发，定位对应 registrar 和最终 refiner 模板。
  • 解释为什么 Context 中既有用户参数，也有 contraction_limit 这类运行时字段。

答案核对

边权文件第一条边如何解析？

文件行 2 1 2 中，2 是 edge weight，pins 是 1 和 2；转为内部 ID 后得到 weight(e0)=2、pins(e0)={0,1}。

为什么 preset 不能替代 -m/-o？

因为 processCommandLineInput 在读取 preset 之前就对命令行 variables_map 调用第一次 notify；mode/objective 标为 required，此时缺失会直接抛出 required_option。

普通 Factory 与 StaticMultiDispatch 的分工是什么？

普通 Factory 用 enum 选 coarsener/refiner 大类；StaticMultiDispatch 再把多个运行时 policy 对象匹配成具体 policy 类型，构造相应模板特化。

结束前的 90 秒口述

从一行 4 7 开始，连续说到 unique_ptr<ICoarsener> 被创建：header → pins → vectors → Hypergraph → CLI/preset → Context → setupContext → enum → registrar map → callback → policy dispatch。中间任何一步卡住，就回到对应章节再走一次。
