02 · Mental Model

同一份拓扑，两种查询方向

超图 H=(V,E) 中，超边可以连接任意多个节点。KaHyPar 的热点操作既需要“给定超边找全部 pin”，也需要“给定节点找全部关联超边”。所以容器同时维护两个方向。

p ∈ e  ⇔  e ∈ I(p)任何修改都必须维持：pin 视角与 incident-net 视角一致。
先纠正一个容易产生的印象_incidence_array 只连续存放各超边的 pins；每个节点的 incident nets 位于节点对象自己的 std::vector。源码注释把两者统称 incidence structure，但物理布局并不完全相同。
03 · Storage

连续 pin 数组 + 每点 incident vector

构造函数先按 hMetis 的 index_vector / edge_vector 建立超边侧的连续区间，再反向扫描 pins，为每个节点填充关联超边列表。

超边视角：连续区间

e0_begin=0, _size=2
e1_begin=2, _size=4
e2_begin=6, _size=3
array[0,2 | 0,1,3,4 | 3,4,6 | …]
⇄

节点视角：独立 vector

v0incidentNets = [e0, e1]
v1incidentNets = [e1]
v3incidentNets = [e1, e2]
v6incidentNets = [e2, e3]
kahypar/datastructure/hypergraph.h · 查询接口
auto incidentEdges(HypernodeID u) const {
  return { hypernode(u).incidentNets().cbegin(),
           hypernode(u).incidentNets().cend() };
}

auto pins(HyperedgeID e) const {
  return { _incidence_array.cbegin() + hyperedge(e).firstEntry(),
           _incidence_array.cbegin() + hyperedge(e).firstInvalidEntry() };
}

为什么删除常用“交换到末尾 + size--”

如果在 vector 中间做 erase，后续元素都要搬移。这里把目标项交换到有效区间末尾，再缩短 _size，有效数据立刻少一个，旧值仍留在边界后方，恢复时还有机会重新纳入有效区间。

物理容量数组空间通常保留，ID 也不重新编号
逻辑有效区间[firstEntry, firstInvalidEntry)
元素有效性_valid=false 后被全局迭代器跳过

initial* 与 current*

接口含义典型用途
initialNumNodes/Edges/Pins构造后确定的原始规模，修改过程不随之下降分配按原始 ID 索引的数组、进度条、边界检查
currentNumNodes/Edges/Pins当前仍有效的逻辑规模停止粗化、统计当前密度、检查收缩进度
nodes() / edges()扫描原始 ID 范围，但跳过 disabled 元素遍历当前有效对象；代价仍与原始范围有关
调试不变量currentNumPins() 在 Debug 断言中会从节点度数之和、超边大小之和各算一遍。两边都必须等于 _current_num_pins。
04 · Partition State

拓扑旁边，还有一组为了“快”而存在的缓存

分区算法会反复询问：节点在哪个块？块有多重？某条超边在每个块有多少 pin？它连接几个块？若每次都扫描整条超边，局部搜索会非常昂贵，因此 Hypergraph 同时维护增量状态。

状态存储位置回答的问题
节点所属块Hypernode::part_idpartID(v) 是多少？
块大小与重量_part_info[k]块是否超重？当前有多少节点？
每边每块 pin 数_pins_in_part[e*k+b]e 在块 b 中有几个 pin？
超边连通度Hyperedge::connectivityλ(e) 连接了几个非空块？
连通块集合_connectivity_sets[e]e 具体连接哪些块？
节点关联 cut 边数num_incident_cut_hes该节点是不是边界节点？
λ(e) = | { b : pinCountInPart(e,b) > 0 } |当某块计数从 0→1，connectivity 增 1；从 1→0，connectivity 减 1。

incrementPinCountInPart 与 decrementPinCountInPart 不只改一个整数，还同步更新 connectivity set 和 λ(e)。这类“派生状态缓存”是性能来源，也是最常见的一致性 bug 来源。

收缩前置条件contract(u,v) 断言 partID(u) == partID(v)。未划分时两者都是 kInvalidPartition；展开阶段则继承代表点的块，保证缓存可恢复。
05 · Contract

contract(u,v)：保留 u，吸收 v

函数先把 v 的重量加到 u，然后逐条遍历 v.incidentNets()。每条边只有两种可能：原来已经含 u，或原来不含 u。

CASE 1 · e contains u and v

共同超边：删除重复 pin v

先把 v 交换到该超边有效区间末尾，再执行 size--。u 已经是 pin，无需给 u 新增 incident edge。

  • edgeHash -= hash(v)
  • edgeSize(e)--
  • 已划分时，同步减少 v 所在块 pin 数
  • currentNumPins--
CASE 2 · e contains v only

独占超边：把 v 的槽改写为 u

pin 数不变；直接把 e 中的 v 改成 u，并向 u.incidentNets 追加 e。

  • hash(v) 替换成 hash(u)
  • 复用最后一个 pin slot
  • u.incidentNets.push_back(e)
  • 块内 pin 数不变，因为 u、v 同块
contract 的骨架（按真实源码压缩）
hypernode(u).setWeight(nodeWeight(u) + nodeWeight(v));

for (HyperedgeID e : hypernode(v).incidentNets()) {
  move_v_to_last_pin_slot(e);
  if (e already contains u) {              // Case 1
    hyperedge(e).decrementSize();
    --_current_num_pins;
  } else {                                  // Case 2
    connectHyperedgeToRepresentative(e, u); // v slot → u
  }
}
hypernode(v).disable();
--_current_num_hypernodes;
return Memento { u, v };
Memento 为什么只有两个 ID？恢复需要的信息大多仍藏在原容器里：v 的 incidentNets 没被清空；Case 1 被截掉的 v 留在有效区间后一格；Case 2 的边可以通过“原本属于 v”这一事实识别。memento 只需记住谁吸收了谁。
06 · Worked Example

手工追踪：在 7 节点实例中执行 contract(4,6)

测试夹具使用 0-based ID，四条超边如下。节点 4 与 6 同时属于 e2，但只有 6 属于 e3，因此一次收缩正好覆盖两种情况。

tests/datastructure/hypergraph_test_fixtures.h
e0 = { 0, 2 }
e1 = { 0, 1, 3, 4 }
e2 = { 3, 4, 6 }   // Case 1: 同时含 u=4, v=6
e3 = { 2, 5, 6 }      // Case 2: 只含 v=6
S0初始计数nodes=7，edges=4，pins=12；w(4)=1，I(4)={e1,e2}，I(6)={e2,e3}
S1合并重量w(4) ← 1+1 = 2
S2处理 e2e2 同时含 4 和 6：删除 pin 6，e2.size 3→2，pins 12→11
S3处理 e3e3 不含 4：把 pin slot 6 改为 4，向 I(4) 追加 e3，pins 保持 11
S4禁用节点 6nodes 7→6；I(6) 仍保留 {e2,e3}，供恢复判断
S5返回记录Memento{u=4,v=6}
currentNumNodes7 → 6
currentNumPins12 → 11
currentNumEdges仍为 4
与测试用例对照仓库测试验证了 nodeIsEnabled(6)==false、代表点重量变 2、代表点度数从 2 变 3，并验证 e2/e3 中都不再出现 6。
07 · Uncontract

恢复不是重建，而是识别旧痕迹

uncontract(memento) 首先重新启用 v、继承 u 的 part ID，然后借助 v 保留下来的 incident list 标记“原本属于 v 的边”。接着扫描 u 当前的 incident list，判断每条标记边应逆转 Case 1 还是 Case 2。

U1restoreMemento启用 v，current nodes +1，v.part_id ← u.part_id
U2markIncidentNetsOf(v)用 fast-reset flag 标记 v 原来的 e2、e3
U3识别 Case 1若超边有效区间后的下一格正是 v，则 size++，把该旧槽重新纳入
U4否则恢复 Case 2从 I(u) 移除这条新增边，把边中复用的 u 槽改回 v
U5恢复代表点w(u) ← w(u)-w(v)，并检查 cut-edge 缓存不变量
为什么强调逆序？收缩会把被截掉的 pin 留在边界后方，也可能连续复用同一批结构。后一次修改建立在前一次结果上，因此多次收缩必须像栈一样后进先出地展开。CoarsenerBase::_history 正是这条恢复栈。
粗化历史的核心形态
// coarsening
_history.emplace_back(_hg.contract(rep, contracted));

// uncoarsening: conceptual form
while (!_history.empty()) {
  _hg.uncontract(_history.back().contraction_memento);
  _history.pop_back();
}

今天需要记住的五条不变量

  • 每个有效 pin 关系必须同时出现在 pins(e) 与 incidentEdges(v) 两个视角。
  • 节点度数之和 = 超边大小之和 = currentNumPins()。
  • disabled 对象仍占原 ID 槽位，但 nodes()/edges() 会跳过它。
  • pinCountInPart、connectivity 和 connectivity set 必须同步变化。
  • 连续修改的恢复顺序必须与修改顺序相反。
08 · Responsibility

收缩原语不等于完整粗化步骤

Hypergraph::contract 的测试明确说明：它不会自行删除 size=1 的超边，也不会自行合并平行超边。真正的粗化入口 CoarsenerBase::performContraction 会在 contract 后追加两步清理。

kahypar/partition/coarsening/coarsener_base.h
void performContraction(HypernodeID rep, HypernodeID v) {
  _history.emplace_back(_hg.contract(rep, v));
  removeSingleNodeHyperedges();
  removeParallelHyperedges();
}
层次职责恢复信息
Hypergraph节点吸收、pin 截短/槽位复用、重量与局部缓存Memento {u,v} + 容器内保留痕迹
HypergraphPruner删除单点超边、检测并合并平行超边被移除边列表与代表边映射
CoarsenerBase组织顺序、保存每层历史、在展开时协调恢复与 refinementvector<CoarseningMemento>
工程上的好处容器提供可测试的最小原语，算法层组合策略性清理。这样可以单独验证“收缩是否正确”，也能替换粗化策略而不重写底层拓扑操作。

先做，再展开答案

题 1：contract(0,2) 的结果是什么？

e0={0}（共同边删除 2），e1 不变，e2 不变，e3 的 2 改为 0。I(0) 从 {e0,e1} 变为 {e0,e1,e3}；nodes=6、edges=4、pins=11。

题 2：为什么 contract(3,4) 少两个 pin？

3 与 4 同时出现在 e1 和 e2；两条边都走 Case 1，各删除一个重复 pin，所以 12→10。不存在仅含 4 而不含 3 的边。

题 3：为什么不在收缩时重新编号？

稳定 ID 让按初始规模分配的缓存、memento、历史记录和外部映射持续有效；代价是全局迭代器要扫描原始 ID 范围并跳过 disabled 项。
